TRIM.IN STRUCTURE OBSERVED IN BOTH INSTALLED EXAMPLES

Ordered records, with explanatory lines between data records:
  1. Title/version line.
  2. Ion heading, then seven values: atomic number, mass (amu), total energy
     (keV), incidence angle (degrees), total count, legacy Bragg field, autosave count.
  3. Calculation heading, then calculation code, random seed, Reminders field.
  4. Output heading, then ranges, backscatter, transmission, sputtering,
     collision control, EXYZ energy increment.
  5. Target heading, then quoted calculation description, atom-entry count N,
     layer count L.
  6. Plot heading, then plot code and minimum/maximum depths (Angstrom).
  7. Atom heading, then N atom records containing descriptive prefix, atomic
     number and mass (amu).
  8. Two layer headings, then L records: layer number, quoted name, thickness
     (Angstrom), density (g/cm3), and N stoichiometric values.
  9. Phase heading, then L phase values (0 solid, 1 gas).
 10. Compound-correction heading, then L correction factors.
 11. Displacement heading, then N energies (eV).
 12. Lattice-binding heading, then N energies (eV).
 13. Surface-binding heading, then N energies (eV).
 14. Stopping-version heading, then selector value.

The installed examples put an additional '0' before the phase heading text.
Do not remove or reinterpret it without a controlled parsing experiment.
The 2013 example's title says SRIM-2012.01; the title is not reliable engine identity.

The atom list represents entries, not unique atomic numbers. The 2013 example
contains separate Si entries for oxide and substrate. Layer stoichiometry is a
matrix with L rows and N columns; damage energies are indexed by atom entry.
This permits distinct damage parameters and tracking for the same element.
Any flattening of a layer/component request must preserve this distinction;
the exact future API and flattening policy have not been proposed or approved.

DOCUMENTED SEMANTICS, NOT NEW EXECUTION VERIFICATION

The output manual calls the ion-line Bragg field unused, retained for backwards
compatibility. It is distinct from the per-layer correction factors, where 1
means no special bonding correction. Reminders semantics remain unresolved.
Numeric fields are documented as free format, including scientific notation.
The input manual says the first 14 characters of atom records are ignored;
exact prefix parsing and padding require verification against the executable.
Quoted layer names support @ for subscript, $ for superscript, _ to return to
normal lettering. Escaping quotes and name-length/encoding limits are unverified.
Plot depths 0 0 request the full target. The window determines stored depth bins.
Do not use the output manual's statement that plot code 0 means no plot:
prior executable checks established code 5 as no graphics (TIN_FINDINGS.txt).
Stopping-version labels conflict between examples/manuals; selector behavior
must be checked independently rather than inferred from heading text.

TRIM.DAT DOCUMENTED FORMAT AND QUALIFICATIONS

Ten header lines; line 8 is the experiment description. Each event is a
five-character identifier followed by eight numeric fields:
  atomic number, energy (eV), X depth (Angstrom), Y (Angstrom), Z (Angstrom),
  direction cosines X, Y, Z.
The recoil example incorrectly says nine numeric fields in its header; its
table and prose specify eight. Spaces or commas are documented separators.
ASCII CRLF lines and final byte 0x1A are documented requirements and were used
in the earlier successful synthetic-event checks. Necessity was not A/B tested.
The manual documents up to 99999 lines, without resolving header/event counting.
Ion setup energy must cover the maximum event energy (TRIM.IN keV versus
TRIM.DAT eV). For recoil input, the event atom must occur in the layer at its
starting depth. Illegal entries may show dialogs and be skipped.
Depth wording says positive, but examples include zero. Exact boundary handling,
direction-vector validation/normalization and multi-species ion behavior remain
unverified; illustrative vectors are not reliable normalized-vector examples.
Recoil statistics are per input event, not necessarily per initiating neutron,
electron or photon. Manual correction for N events from M particles is N/M;
automatic normalization is outside the current unapproved implementation scope.

COMPOUND CORRECTION COMPARISON

SR.IN's target record has one Compound Corr. value for its homogeneous target.
TRIM.IN has one factor per layer under Target Compound Corrections (Bragg).
The manual describes these as chemical-bonding corrections to electronic
stopping, with 1 meaning no special bonding correction. They represent the
same kind of correction, applied to SR's target versus TRIM's individual layers.
The legacy Bragg Corr slot on TRIM's ion line is separately documented unused.
Project SR rendering writes correction.applied_factor into SR.IN's target slot.
No new cross-engine numerical-equivalence experiment was performed; matching
the correction factor alone does not establish identical SR/TRIM results.

DICTIONARY VISIBILITY FOLLOW-UP

The user could see choices after automation stopped, and reported liquid-water
correction 0.94 in both interfaces. Current-window visual captures independently
confirmed both displayed fields at 0.94; saved-file precision is still unchecked.
The TIN window showed Water_Liquid with hydrogen/oxygen composition. The SR
main window still had an empty target composition despite its 0.94 field, so its
field alone is not an independent saved compound-generation check.

Further inspection established a working dictionary interaction method:
  - list_windows and list_apps enumerate only the main SR window, not its
    Common Compounds secondary window, even while the dictionary is visible.
  - get_window_state(include_text=False) can return two separate screenshots,
    each with its own ID, origin, size and z-order: main SR and dictionary.
  - Activating the main SR window brought it in front of the dictionary and
    partially obscured the dictionary capture.
  - Clicking Water (liquid) through the dictionary screenshot's own ID and
    coordinates brought the dictionary forward and visibly selected the entry.
    A subsequent screenshot showed its complete readable compound list.
  - Screenshot ordering changed with z-order. Do not assume index 0 is always
    the main window or always the dictionary; inspect each returned image.

Thus dictionary invisibility is not a universal program failure. Secondary-window
enumeration and foreground/capture targeting demonstrably contributed to the
automation problem. The dictionary's lower explanatory panel displayed symbol
glyphs while the compound list was readable; its font/encoding cause was not
established. An accessibility-only inspection of the main window succeeded but
contained no dictionary controls. This does not establish whether querying the
foreground dictionary's accessibility tree triggers the earlier COMCTL32 faults.
Those logged faults are real but their exact trigger remains unresolved.
The successful dictionary and the user's current windows were left open.
